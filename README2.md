## Задача 3: API Gateway * (необязательная)

### Есть три сервиса:

**minio**
- хранит загруженные файлы в бакете images,
- S3 протокол,

**uploader**
- принимает файл, если картинка сжимает и загружает его в minio,
- POST /v1/upload,

**security**
- регистрация пользователя POST /v1/user,
- получение информации о пользователе GET /v1/user,
- логин пользователя POST /v1/token,
- проверка токена GET /v1/token/validation.

### Необходимо воспользоваться любым балансировщиком и сделать API Gateway:

**POST /v1/register**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/user.

**POST /v1/token**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/token.

**GET /v1/user**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис security GET /v1/user.

**POST /v1/upload**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис uploader POST /v1/upload.

**GET /v1/user/{image}**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис minio GET /images/{image}.

### Решение 1

* Чтобы сделать единую точку входа для микросервисов, я посмотрел три популярных бесплатных решения: NGINX (как шлюз), Kong Gateway и Traefik.

Сравнение решений:

| Критерий | NGINX (бесплатный) | Kong Gateway (бесплатная версия) | Traefik |
| --- | --- | --- | --- |
| Маршрутизация | Есть, но настраивается вручную в файлах — при каждом изменении нужно перезапускать сервис | Есть, гибкая — настраивается через файлы или API без перезапуска | Есть, сама подхватывает изменения из конфигов и Docker/Kubernetes |
| Проверка логина | Только простые варианты; JWT и OAuth2 — либо платно (NGINX Plus), либо через доп. модули | Всё из коробки: JWT, OAuth2, API‑ключи и другие плагины | Простейшее из коробки; JWT и OAuth2 требует отдельного сервиса проверки |
| HTTPS | Отлично справляется, производительный | Поддерживает, умеет управлять сертификатами | Поддерживает, плюс сам получает сертификаты Let's Encrypt автоматически |
| Насколько легко настроить | Начать просто, но сложные правила пишутся вручную | Средняя сложность, зато много настроек для микросервисов | Начать проще всего, особенно если работаешь с Docker или Kubernetes |


* Я выбираю Kong Gateway.
* Вход по логину уже встроен. Бесплатный NGINX не умеет проверять токены, пришлось бы делать скрипты или ставить отдельный сервис. В Kong это просто плагины, включаются быстро.
* Удобная маршрутизация. Kong направляет запросы к нужному сервису по настройкам, которые можно менять без перезапуска — это удобно для автоматизации.
* HTTPS. Kong сделан на базе NGINX, поэтому сам расшифровывает HTTPS на входе и снимает эту нагрузку с внутренних сервисов.
* Задел на будущее. Система растёт для крупной компании, а там понадобятся лимиты запросов, логи и метрики. В Kong всё это уже есть в виде плагинов.



### Решение 2

* Для организации асинхронного взаимодействия между микросервисами я сравнил три популярных решения: RabbitMQ, Apache Kafka и Redis (Pub/Sub и Streams).

| Критерий / Требование | RabbitMQ | Apache Kafka | Redis (Streams) |
| --- | --- | --- | --- |
| Поддержка кластеризации, надёжность. | Да, встроенная кластеризация и репликация очередей (Quorum Queues) | Да, высокая отказоустойчивость за счёт партиций и реплик | Да (Redis Cluster / Sentinel), но надёжность ниже при сбоях |
| Хранение сообщений на диске | Да, поддерживает persistent-сообщения с записью на диск | Да, по умолчанию пишет весь поток событий на диск | Частично (основная работа в оперативной памяти, сброс на диск с задержкой) |
| Высокая скорость работы | Высокая (десятки тысяч сообщений в секунду, низкие задержки) | Очень высокая (сотни тысяч и миллионы сообщений в секунду) | Очень высокая (так как работает в оперативной памяти) |
| Поддержка разных форматов сообщений | Да, не зависит от формата (передаёт любые байты: JSON, XML, Protobuf) | Да, работает с массивом байтов (JSON, Avro, Protobuf и др.) | Да, работает со строками и байтами (JSON, текст и т.д.) |
| Разделение прав доступа к потокам | Да, гибкая система пользователей, виртуальных хостов (vhost) и прав (ACL) | Да, настройка прав доступа через ACL для конкретных топиков | Ограниченная (в новых версиях есть ACL, но разделение по потокам менее гибкое) |
| Простота эксплуатации | Средняя / высокая (есть удобный встроенный веб-интерфейс, легко развернуть) | Сложная (требует тонкой настройки, много ресурсов и сложного администрирования) | Высокая (очень легко запускается и настраивается) |

* Выбираю RabbitMQ.
* Надёжность: умеет собираться в кластер и сохраняет сообщения на диск, чтобы они не пропали при сбое.
* Баланс скорости и простоты: проще в настройке, чем Kafka, есть удобная веб-панель, а скорости для наших задач хватит с запасом.
* Разделение прав: можно гибко настроить доступы и виртуальные хосты (vhost) для разных сервисов.
* Любые форматы: ему всё равно, в каком виде использовать данные (JSON, XML и др.).
