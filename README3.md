# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

### Решение 1

* Выбираю GitLab т.к. это всё вместе: хранилище кода, сборка и проверка CI/CD, место для готовых файлов. Не надо соединять разные программы, всё уже работает.

1. Для каждого микросервиса — свой репозиторий.
2. Разработчик отправляет код — GitLab запускает сборку.
3. Автоматически идут тесты. Если есть ошибка, то процесс останавливается, разработчик получает уведомление.
4. Если тесты прошли, программа сохраняется как артефакт или Docker‑образ.
5. Система сама ставит сервис на тестовые стенды. На рабочий сервер выкладывают только после ручного подтверждения.

* Этот выбор подходит потому что;

1. Работает в облаке, не нужно устанавливать.
2. Можно сделать сколько угодно репозиториев — по одному на сервис.
3. Сборку можно запускать автоматически или вручную.
4. Сценарий сборки пишут в файле .gitlab-ci.yml и в него можно добавить любые шаги и шаблоны.
5. Пароли и ключи хранят в защищённом разделе и они не видны в коде.
6. Можно использовать свои Docker‑образы и свои серверы.
7. Сборки и тесты можно делать параллельно — это экономит время.

### Решение 2

* Выберу стек Fluent Bit + Kafka + Elasticsearch + Kibana (EFK).

1. Сервисы пишут логи в stdout — ничего в коде менять не надо.
2. Fluent Bit на каждом сервере собирает эти записи и отправляет дальше.
3. Kafka держит логи в очереди — если хранилище недоступно, данные не пропадут.
4. Elasticsearch хранит и индексирует логи — можно быстро искать среди миллионов строк.
5. Kibana — веб‑интерфейс для поиска, графиков и фильтров.

* Этот выбор подходит потому что;

1. Сбор со всех хостов сразу.  Fluent Bit стоит на каждом сервере и шлёт логи в одно место.
2. Минимум требований к приложениям: достаточно писать в stdout.
3. Fluent Bit буферизует на диске, Kafka страхует при сбоях.
4. Elasticsearch быстро ищет по тексту, времени, сервису, уровню ошибки.
5. В Kibana настраивают права, чтобы разработчики видели только свои сервисы.
6. В Kibana любой запрос можно сохранить и скинуть коллеге ссылку.

### Решение 3

* Для мониторинга возьму связку Prometheus + Grafana + Node Exporter + cAdvisor.

1. Node Exporter ставится на каждый сервер и собирает данные о железе: CPU, RAM, диск, сеть.
2. cAdvisor следит за контейнерами и показывает, сколько ресурсов тратит каждый сервис.
3. Библиотеки в коде сервисов отдают специфические метрики. Например, время ответа или число ошибок.
4. Prometheus сам забирает все эти цифры с серверов и сервисов и хранит их.
5. Grafana рисует графики и дашборды. В ней удобно смотреть, что происходит в системе.

* Этот выбор подходит потому что;

1. Собирает метрики со всех серверов и сервисов;
2. Показывает и нагрузку на железо, и потребление ресурсов каждым сервисом;
3. Позволяет выводить любые нужные показатели из кода;
4. Даёт язык запросов PromQL для расчётов и агрегации;
5. В Grafana можно настроить любые панели под разные задачи.
